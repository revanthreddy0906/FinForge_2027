# ADR-0001: Registration database design

**Status:** Proposed
**Date:** 2026-11-26
**Deciders:** Revanth (FinFoundry)

## Context

FinForge 2027 needs to store team registrations, contact-form messages and a list of organizers
who may view and export registrations. The constraints come from `CLAUDE.md`:

- About 75 teams. One leader registers each team. Teams have 2 to 5 members, leader included.
- Design target of 1,000 concurrent visitors (2,000 margin) when registration opens, but only
  about 75 to 150 registration writes in total. Public pages never touch the database.
- Team name and leader email must be unique. A double click or retry must never create a
  duplicate (idempotency key).
- A team cap, if any, must be enforced in the database, not only in UI code.
- Row Level Security on every table. The public can never read any team's data.
- Admins sign in with Supabase Auth and are limited to an allow-list of organizer emails.
- Collect only what registration needs.
- Supabase project `FinForge_2027` (ref `nsfzmtlfspcghuyurwkz`, Mumbai, Postgres 17), currently
  empty.

## Decision

### Write path: server-only RPC, no direct public inserts

The browser never talks to the registration tables. The registration route handler (server)
validates with Zod, verifies Turnstile, applies the Upstash rate limit, then calls one Postgres
function, `public.register_team(payload jsonb)`, using the service-role key over supabase-js
(HTTP/PostgREST, no raw connections).

The `anon` and `authenticated` roles get **no** insert, update or delete privilege on any table and
cannot execute `register_team`. The anon key is public, so a direct anon insert policy would let
anyone skip Turnstile and the rate limit by calling PostgREST themselves. RLS stays enabled on
every table as a second wall.

`register_team` runs in one transaction and:

1. Takes a transaction-level advisory lock, so concurrent registrations are serialized. At 75 to
   150 writes in total this costs nothing and makes the cap check race-free.
2. If the idempotency key already exists, returns the existing team instead of inserting again.
3. Checks the team cap from `event_settings`; raises `event_full` if reached.
4. Inserts the team and its members. Unique constraints raise `team_name_taken`,
   `leader_email_taken` or `member_email_taken`, which the route maps to friendly messages.
5. Returns the team id and a short human-readable reference (e.g. `FF27-0042`) for the
   confirmation email.

### Tables (all in `public`, RLS enabled, no public grants)

**`teams`**

| Column            | Type          | Notes                                                 |
| ----------------- | ------------- | ----------------------------------------------------- |
| `id`              | `uuid` PK     | `gen_random_uuid()`                                   |
| `reference`       | `text` unique | `FF27-0001`, from an identity sequence                |
| `team_name`       | `text`        | 2 to 60 chars, trimmed; unique case-insensitively     |
| `institution`     | `text`        | College name, 2 to 120 chars                          |
| `leader_name`     | `text`        | 2 to 80 chars                                         |
| `leader_email`    | `text` unique | lowercase and trimmed (check constraint), max 254     |
| `leader_phone`    | `text`        | Indian mobile, `+91` and 10 digits (check constraint) |
| `idempotency_key` | `uuid` unique | Generated by the form once per attempt                |
| `status`          | `text`        | `registered`, `withdrawn` (check constraint)          |
| `consent_version` | `text`        | Which privacy note the leader accepted                |
| `created_at`      | `timestamptz` | `now()`                                               |

**`team_members`** (includes the leader as position 1)

| Column       | Type          | Notes                                                    |
| ------------ | ------------- | -------------------------------------------------------- |
| `id`         | `uuid` PK     |                                                          |
| `team_id`    | `uuid` FK     | `on delete cascade`, indexed                             |
| `position`   | `smallint`    | 1 to 5, unique per team; 1 is the leader                 |
| `full_name`  | `text`        | 2 to 80 chars                                            |
| `email`      | `text` unique | lowercase; unique across all teams (one team per person) |
| `created_at` | `timestamptz` |                                                          |

Team size 2 to 5 is enforced by a **deferred constraint trigger** that counts members per team at
commit time, plus the `position between 1 and 5` check. A team can never be saved with 1 or 6
members, whichever code path writes it.

**`event_settings`** (single row, `id = true`)

| Column      | Type      | Notes                               |
| ----------- | --------- | ----------------------------------- |
| `max_teams` | `integer` | Null means no cap. `TODO: team cap` |

Registration open/closed/coming-soon stays in `src/config/event.ts`, as `CLAUDE.md` says. The
server route refuses writes when the config is not `open`.

**`contact_messages`**

| Column       | Type          | Notes                                |
| ------------ | ------------- | ------------------------------------ |
| `id`         | `uuid` PK     |                                      |
| `name`       | `text`        | 2 to 80 chars                        |
| `email`      | `text`        | lowercase, max 254                   |
| `message`    | `text`        | 10 to 2,000 chars                    |
| `handled_at` | `timestamptz` | Set by an admin; null until answered |
| `created_at` | `timestamptz` |                                      |

Stored as a backup in case the Resend notification email fails. Inserted server-side only, same
as registrations.

**`admin_allowlist`**

| Column     | Type          | Notes     |
| ---------- | ------------- | --------- |
| `email`    | `text` PK     | lowercase |
| `added_at` | `timestamptz` |           |

Organizer emails are inserted by hand (SQL editor), never committed to the repo.

### Admin access

- `public.is_admin()`: `security definer`, `search_path = ''`, returns true only when the JWT
  email is in `admin_allowlist`. Execute granted to `authenticated` only.
- RLS select policies on `teams`, `team_members` and `contact_messages` for `authenticated` users
  where `is_admin()`. Update policy on `contact_messages.handled_at` for admins. No admin deletes
  through the API.
- A `security_invoker` view `admin_registrations` (one row per member, team columns joined) backs
  the CSV export, so it obeys the same RLS.
- Supabase Auth: email OTP / magic link, public sign-ups disabled, admin users created by hand.

### Migrations and types

- SQL lives in `supabase/migrations/<timestamp>_<name>.sql` and is applied with the Supabase MCP
  `apply_migration` using the same names, so the repo and the database history match.
- `get_advisors` (security and performance) is run after every migration and every warning fixed.
- Types are generated into `src/lib/supabase/database.types.ts`.

## Options considered

### Option A: Server-only RPC with service role (chosen)

| Dimension   | Assessment                                                    |
| ----------- | ------------------------------------------------------------- |
| Complexity  | Medium: one SQL function plus constraints                     |
| Cost        | Free tier is enough                                           |
| Scalability | Writes are tiny; public pages never hit the DB                |
| Security    | Turnstile and rate limit cannot be bypassed; no public grants |

**Pros:** One atomic transaction for team plus members, race-free cap, idempotent, and the anon key
grants nothing. **Cons:** The service-role key must stay server-only (enforced with
`import 'server-only'`).

### Option B: Anon insert policies, browser writes directly

**Pros:** No server route. **Cons:** Anyone with the public anon key can bypass Turnstile and the
rate limit; team and members are two separate inserts, so half-written teams and cap races are
possible. Rejected.

### Option C: Store members as a `jsonb` array on `teams`

**Pros:** One table, one insert. **Cons:** Member emails can't have a unique constraint, CSV export
and per-member check-in get harder. Rejected.

## Consequences

- Easier: duplicate and full-event handling is guaranteed by the database, so the UI only maps
  error codes to messages.
- Easier: admin export is one view under RLS.
- Harder: every new write path must go through a server route or SQL function.
- Revisit: the team cap number, any extra fields (tracks, year of study, T-shirt size), and a
  data-retention date for deleting personal data after the event.
